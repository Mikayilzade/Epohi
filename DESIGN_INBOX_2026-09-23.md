# Design Inbox — 2026-09-23

Temporary inbox for ideas discussed on 2026-09-23. This is **not** a canonical
accepted-design document. Section 1 preserves USER NOTES; section 2 records
CHATGPT ANALYSIS separately. Neither section authorizes implementation.

## Status rules

Use only `IDEA`, `PROPOSAL`, `QUESTION`, and `UNCLEAR` for entries in this inbox.
An idea moves to canonical design only after a separate, explicit user decision.
Keep ambiguous wording as a question rather than supplying an answer silently.

## 1. USER NOTES — preserve source intent

### Battle Simulator — IDEA

- Отдельный мини-режим/мини-игра «Эпохи: симулятор боя».
- Игрок выбирает стандартную карту из списка, затем формирует свой и вражеский
  состав. Возможен `autofill`.
- Лимиты, составы, баланс и правила нужно продумать отдельно.
- Цель первой версии — один бой между выбранными сторонами «для фана».
- Пользователь хочет быстро получить удовольствие от игры: не за недели, а
  ориентировочно за один день. **UNCLEAR:** это ориентир для первого играбельного
  опыта, а не подтверждённый срок или утверждённый объём MVP.

### Squad / battalion / army hierarchy — IDEA / QUESTION

- Отряд: один командир и минимум два воина того же типа. Командир более опытный.
- Возможные показатели опыта командира: сколько ударов пережил; сколько боёв
  пережил; скольким убийствам помог; сколько противников добил.
- Логику опыта и баланс нужно отдельно продумать.
- Для формирования отряда бойцы должны быть на одной клетке или близко друг к
  другу. **QUESTION:** что именно означает «близко»?
- Несколько отрядов могут формировать батальон; несколько батальонов — армию.
  Генерал армии может выбираться из командиров.
- Все уровни и правила иерархии требуют отдельного проектирования.

### Separate repository / reuse — PROPOSAL

- Сначала сделать мини-игру в отдельном репозитории.
- Рассмотреть два варианта: использовать наработки Epohi или начать минимально
  с нуля.
- Позже потенциально включить Battle Simulator как отдельный mini mode в
  большую Epohi. Пока не нагружать основную игру этой системой.

### Design-before-code — PROPOSAL

- Перед началом обсудить все нюансы и отдельно обсудить графику.
- Сначала просмотреть готовые предложения и выбрать.
- Никакой реализации, пока остаются содержательные уточняющие вопросы.
- Вопросы должны быть короткими: несколько вариантов ответа плюс возможность
  дать собственный вариант пользователя.
- Каждый этап и механику можно обсуждать долго; качество логики важнее
  скорости начала реализации.

### Future game 1 — production/training — IDEA

- Отдельная игра/режим вокруг производства и подготовки юнитов.
- Возможные системы: производство юнитов; крафт экипировки и оружия;
  тренировка навыков; тренировка характеристик.
- Разные настройки должны давать разные стратегии. Пример: за одинаковый
  период один игрок делает одного сильного бойца, другой — десять слабых.
- В следующем боевом раунде подкрепления приходят на основе ранее принятых
  производственных решений.

### Future game 2 — continuous battle — IDEA

- Бой на базе Battle Simulator, но подкрепления продолжают приходить, пока у
  стороны остаётся хотя бы один живой воин.
- Когда все погибли — поле/позиция потеряна.
- Позже эти системы потенциально можно вплести в большую Epohi.

### Separate recruitment/training project — QUESTION

- Стоит ли этап набора/подготовки армии сделать отдельной мини-игрой до
  объединённой игры «подготовка + бой»?

### Turn structure — IDEA / UNCLEAR

- Бой предполагается пошаговым.
- Исходная идея пользователя: каждой стороне даётся количество действий,
  связанное с количеством боевых единиц на арене.
- Примеры пользователя: отряд из 3 воинов → 3 удара/действия; батальон из
  5 отрядов → 5 ударов/действий.
- **UNCLEAR:** примеры могут считать действие на разных уровнях — человек и
  отряд. Это требует вопроса, а не автоматического выбора формулы.

### Commander intelligence / tactics / skills — IDEA / QUESTION

- На этапе тренировки можно выбирать тактики, стратегии и навыки.
- Доступность зависит от характеристик. Пример: если интеллект командира
  позволяет, можно выбрать максимум 5 особенностей.
- Выбирать можно только особенности, доступные по порогам характеристик.
- Отдельно определить список характеристик, список навыков, зависимости,
  ограничения и баланс.

### Scale from individuals upward — PROPOSAL

- Сначала создать логику отдельных индивидов, затем масштабировать её до
  отрядов, батальонов и армий.

### Formation / survivability idea — IDEA / QUESTION

- Отряд может на текущий ход выставлять вперёд наиболее живучего бойца.
- При одинаковом HP передний может выбираться произвольно; после ранений
  вперёд становится более целый/живучий.
- Передний получает больше урона, задние — меньше. Значительно лучше
  экипированный боец может оставаться впереди дольше.
- «Живучесть» предполагается как комбинация HP, брони, определённых навыков
  и, возможно, других параметров.
- Нужна отдельная формула урона и живучести.

### Movement rethink for Epohi — PROPOSAL

- Пользователь считает текущую базовую стоимость движения Epohi ошибочной.
  Это оценка пользователя, а не утверждение, что код уже изменён.
- Новое предложение: труднопроходимая местность без бонусов — cost `1`;
  обычная местность — cost `0.5`.
- Очки движения юнитов определить отдельно. Стартовая гипотеза: пешие —
  `1 movement point`, разведчики — `2`, всадники — `3`.
- Для летающих cost `0.5` независимо от ландшафта.
- Возможные модификаторы: дороги, terrain perks, «вдохновение» или аналоги.
- Это предложение, а не принятое изменение текущей игры.

### Movement visualization / UX — PROPOSAL

- При выборе юнита показывать зоны достижимости.
- Предложенные цвета: текущая клетка — синяя; доступный противник для атаки —
  красный; достижимо сейчас — зелёный; за 2 хода — жёлтый; за 3 — оранжевый;
  за 4 — фиолетовый.
- Цель — сразу видеть маршруты и варианты действий.
- Отдельная кнопка «Идти» потенциально больше не нужна.
- Предложенное взаимодействие: (1) нажать юнита, (2) сразу увидеть зоны,
  (3) нажать клетку назначения.

### Mini-sim-first development principle — PROPOSAL

- Не писать и не тестировать сразу всю большую игру.
- Для каждой существенной механики сначала делать маленькую игру/симулятор,
  затем объединять проверенные механики.
- Графические решения тоже сначала проверять на малых примерах.

### Performance / memory investigation — QUESTION

- Отдельно понять, что реально нагружает игру во время партии.
- Возможные факторы для измерения: число городов, юнитов и клеток; история
  прошлых ходов; состояние текущего хода; действия; другие runtime/state/render
  факторы.
- Не устанавливать лимиты заранее без измерений.

### Worker removal proposal — PROPOSAL

- Убрать крестьян/workers из Epohi — крупная design-перемена, не мелкая правка.
- Альтернативная модель: улучшение становится доступно после науки; игрок
  нажимает непосредственно на ресурс/клетку и строит при наличии производства
  и/или золота.
- Отдельно определить виды улучшений, стоимость, производственные требования,
  золото и влияние на текущие worker-системы.

### Before discussing the above — PROPOSAL / QUESTION

Пользователь хочет сначала:

1. Пройти короткий «Git для чайников» с ChatGPT и, при желании, YouTube.
2. Понять, почему накопилось столько веток/PR/worktrees.
3. Понять текущее положение проекта.
4. Решить, можно ли сократить Git-структуру до понятного минимума.
5. Понять, продолжать ли каждый новый Codex-chat через отдельные ветки или
   перейти к более простой схеме.

**UNCLEAR:** порядок выше ставит Git-ориентацию перед наведением порядка в
ветках; рабочий порядок в разделе 2.L ставит Git cleanup перед курсом.
Сохранены оба порядка; при планировании спросить пользователя, какой нужен.

## 2. CHATGPT ANALYSIS — current conclusions, not user decisions

### A. Four-layer development path — PROPOSAL

Предварительно видны четыре слоя: (1) Battle Simulator, (2) Production /
Training Simulator, (3) объединённая игра «подготовка + бой с подкреплениями»,
(4) поздняя интеграция проверенных механик в Epohi. Это анализ, а не решение.

### B. Best first experiment — PROPOSAL

Battle Simulator выглядит лучшим первым кандидатом: отдельный репозиторий,
минимальная зависимость от большой Epohi, возможность позже переиспользовать
идеи/алгоритмы. Предлагаемый MVP: `map → two force compositions → one battle →
result`. Это соответствует желанию быстро получить играбельный fun prototype;
срок и объём ещё не утверждены.

### C. Important abstraction conflict — QUESTION

«3 воина в отряде = 3 действия» предполагает individual-level actions;
«5 отрядов в батальоне = 5 действий» — squad-level actions. До реализации
нужно выбрать один вариант: (1) каждый человек остаётся action unit на всех
масштабах, (2) на более крупном масштабе action unit становится отряд,
(3) гибрид, (4) свой вариант пользователя.

### D. Hierarchical simulation principle — PROPOSAL

Не создавать независимую боевую формулу для каждого масштаба. Предпочтительная
гипотеза: `individual stats → squad derived stats → battalion aggregation →
army/general modifiers`. Пока это только предложение.

### E. Commander experience — PROPOSAL

Не связывать опыт только с числом пережитых ударов. Возможные факторы: участие,
выживание в боях, assists, kills, finishing blows, эффективность подразделения
под командованием. Звёзды лучше показывают накопленный опыт, а не становятся
отдельной «магической» характеристикой.

### F. Survivability / front-line model — PROPOSAL

Динамический выбор переднего бойца выглядит перспективно. Survivability лучше
считать derived value: HP + armor + defensive skills + condition + возможные
другие параметры. Формула пока не определена.

### G. Production simulator after combat — PROPOSAL

Сначала проверить, что бой «1 сильный против многих слабых» интересен и
математически работает. Затем балансировать производство, обучение, крафт и
подкрепления.

### H. Movement proposal — PROPOSAL

Модель `0.5 normal / 1 difficult` плюс отдельные movement points выглядит
гибче текущей. Она даёт пространство для дорог, perks, terrain effects и
различной мобильности юнитов. До обсуждения и прототипа это предложение.

### I. Movement overlay caution — PROPOSAL / QUESTION

Зелёная зона «достижимо сейчас» выглядит естественно. Многослойная карта
2/3/4 ходов может улучшить планирование, но также перегрузить интерфейс и
увеличить стоимость pathfinding. Её лучше прототипировать отдельно.

### J. Worker removal is a major decision — QUESTION

Удаление workers фундаментально меняет модель, особенно после работы над
worker projects/progress/actions/specialization. До кода нужно отдельно решить:
(1) оставить workers, (2) убрать, (3) гибрид.

### K. Performance — PROPOSAL

Прежде чем ограничивать города/юниты/карту, провести измеряемый performance
audit. Возможные bottlenecks: DOM/tile count, rendering, pathfinding, AI,
число городов/юнитов, history/state, saves, visuals/assets и другие runtime
процессы.

### L. Recommended near-term order — PROPOSAL / UNCLEAR

Рабочая последовательность обсуждения из разговора, не утверждение новых
игровых механик:

1. Сохранить этот design inbox.
2. Привести Git/PR/worktree структуру Epohi в понятное состояние.
3. Пройти короткий Git-for-beginners курс.
4. Подробно спроектировать Battle Simulator без кода.
5. Утвердить минимальный one-day MVP.
6. Создать отдельный репозиторий.
7. Реализовать и поиграть.
8. Только после проверки боя проектировать Training/Production Simulator.
9. Затем решить, объединять ли их.
10. Переносить успешные системы в Epohi только после проверки.

**UNCLEAR:** пользовательская последовательность в разделе 1 ставит короткий
курс Git первым. Порядок курса и Git cleanup нужно подтвердить до этих этапов.

Рабочее правило общения: пока есть содержательный design question, реализацию
не начинать. Вопросы задавать коротко, предпочтительно 2–5 вариантов ответа
плюс «свой вариант» пользователя.
